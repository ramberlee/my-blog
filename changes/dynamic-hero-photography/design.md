# Design: 动态摄影作品 Hero 网格

## Facts and Constraints

- 配置当前通过 `storage.ts` 的 `config.json` 映射持久化到 SQLite，`heroImages` 已作为 JSON 数组存储，无需数据迁移。
- `PUT /api/config` 已支持提交 `heroImages`，但前端把渲染和编辑都写死为 3 个槽位。
- 上传接口 `POST /api/upload/image` 已返回 `url`，可复用于摄影作品上传。
- 前台为 React + 内联样式 + CSS 变量，现有主题为暖色深/浅双主题与古铜色强调色。
- 项目已安装 `@dnd-kit`，但本次范围明确不包含拖拽排序。

## Goals

- 支持任意数量的摄影作品配置、展示与后台维护。
- 保持现有视觉身份，仅重构 Hero 图片网格和配置编辑区。
- 不新增 API 端点、不引入新数据表、不改变现有认证边界。

## Non-goals

- 拖拽排序、图片分类、独立相册页面。
- 上传文件管理库或独立的摄影作品数据表。
- 修复 `/api/config` 与 `/api/upload` 缺少服务端认证中间件的既有问题。
- 首页整体视觉主题重设计。

## Decisions

### Decision 1: 继续使用 `heroImages` 数组，不新增摄影作品端点

Choice: 保持 `SiteConfig.heroImages: HeroImage[]` 作为唯一数据源，前后端共用同一结构。

Rationale: 现有配置存储、GET/PUT 接口和后台编辑区已经围绕该字段建立；任意数量只是放宽校验与交互，不引入第二个状态源。

Alternatives: 新增 `/api/photos` 集合接口；需要额外的存储、迁移和状态同步，收益不匹配本次范围。

Consequences: 配置体量由数组长度决定，但单个 5MB 上传上限和 JSON 请求体已有天然约束。

### Decision 2: 使用响应式 CSS Grid 动态排列，不引入 JS 瀑布流库

Choice: Hero 网格使用 CSS Grid 与条件类名；首图在桌面端占据更大的跨列区域，其余图片按统一网格填充；移动端降为单列或双列。

Rationale: 无需新增依赖，能对任意数量自适应，同时保持现有非对称视觉语言。

Alternatives: 使用 `react-masonry` 等瀑布流库；会增加依赖和重排成本，且与现有内联样式风格不一致。

Consequences: 图片保持统一 `object-fit: cover`，宽高比由网格轨道决定，需要人工控制网格行高避免出现过高或过空的单元格。

### Decision 3: 后台编辑区使用可增删的条目列表

Choice: 在“首页摄影作品”编辑区为每个条目渲染缩略图、上传按钮、URL 输入框、描述输入框和删除按钮，并提供“添加图片”按钮；新条目使用 `crypto.randomUUID()` 生成 `id`。

Rationale: 与现有配置编辑的保存模型一致，只修改本地表单，点击“保存配置”后统一 PUT。

Alternatives: 每条保存立即写接口；会增加请求次数与失败恢复复杂度。

Consequences: 编辑期间的删除/新增只在保存后生效，用户需要明确点击保存；界面文案需提示这一点。

### Decision 4: 服务端校验字段但不限制数量上限

Choice: `PUT /api/config` 校验 `heroImages` 为数组且每项 `id`、`url`、`alt` 均为非空字符串，不设置固定数量上限。

Rationale: 用户明确表示不知道会上传多少张，固定上限会重新制造“固定槽位”问题；请求体大小本身已构成边界。

Alternatives: 上限 12/30 张；不可验证的业务上限会违背需求。

Consequences: 极大数组可能拖慢保存，但现有 5MB 单图和 JSON 请求体限制已能接受。

### Decision 5: 空数组不渲染摄影网格

Choice: 当配置中显式保存 `heroImages: []` 时，首页完全不渲染摄影网格，也不显示空状态文案；默认占位图只用于配置缺失 `heroImages` 字段的初始状态。

Rationale: 默认占位图是第三方图片，若用户清空配置后继续显示，会与“展示我的摄影作品”的意图冲突；空状态文案会占据 Hero 视觉空间，而用户希望清空后如同网格不存在。

Alternatives: 空数组回退默认图，或显示“摄影作品整理中”空状态；前者误导用户，后者破坏“网格不存在”的预期。

Consequences: 首次部署但未保存配置的站点仍能看到默认图；后台保存空数组后首页 Hero 区域只保留原有标题与文案，行为可预期。

### Decision 6: 图片较多时使用“精选拼贴 + 展开全部”

Choice: 当 `heroImages` 超过 8 张时，Hero 先展示前 6 张组成的精选拼贴，并渲染一个“展开全部 N 张作品”的图片卡入口；点击后原地展开包含全部图片的紧凑画廊，再次点击可收起。所有图片使用 `LazyImage` 懒加载，展开入口使用原生 `<button>` 与 `aria-expanded`。

Rationale: 摄影作品数量不可预知，直接全部平铺会让 Hero 高度失控；只展示 6 张又会让其余作品失去入口。精选拼贴保留编辑感，带数量与缩略图的展开卡既是入口也是视觉元素，展开后才加载剩余图片，兼顾叙事、完整性和性能。

Alternatives: 全部平铺成 `auto-fill` 多列网格；实现简单但数量多时页面过长且缺少探索感。横向胶片条；高度稳定但偏离“网格”形态且桌面发现性弱。

Consequences: 需要维护展开/收起状态与可访问性语义；组件测试需要覆盖 6 张、20 张、展开后 20 张、收起后恢复 6 张的场景。

## Risks and Verification

- 动态网格在图片数量少时可能显得空：通过首图跨列和统一网格轨道缓解，并用组件测试固定 1/2/5 张场景。
- 空数组完全不渲染网格：组件测试断言不存在网格容器与空状态文案，避免误判为加载失败。
- 服务端校验收紧后旧数据缺少 `id` 可能被拒绝：存量配置已含 `id`，测试覆盖 3 项存量配置原样返回。
- 超多图片导致首屏变慢或布局过高：8 张以上先展示 6 张精选拼贴，展开后再加载全部图片并使用懒加载；组件测试覆盖阈值与展开/收起行为。
- 文档与实现漂移：任务清单包含 README/API/JSDoc 同步，并由测试和 lint 验证。
